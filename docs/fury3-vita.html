What was built

Microsoft Fury³ shipped in 1995, developed by Terminal Reality: eight planets, a 24-mission campaign, a software renderer, tracker music and full-motion video. This project takes the original 645 KB FURY3.EXE, translates every function to C, and links that code to a new runtime that stands in for Windows. The same translated code now builds for Windows, Linux and the PS Vita.

Going by file timestamps, it took about 24 hours from the disc image reaching the PC to a Vita build with controls, sound, music, saving and first-launch setup. That speed rests on the existing sp00nznet pcrecomp toolchain, which supplied the disassembler, the translator and an early runtime.

Breakthroughs

What stands out

Other x86-to-Vita recompilations exist, including Project I.G.I. and Hollywood Monsters, so the method itself is not new. These are the parts that are unusual, or that we could not find done anywhere else.

Fury³ in your hands

We found no earlier handheld port of this game. It runs as native ARM code at about 80 fps in quiet flight on a 444 MHz handheld from 2011.

Hand rewrites with proof

The two hottest assembly routines were rewritten in C. A verifier ran old and new versions on identical copies of the whole 69 MB guest memory and compared every byte, register and flag: 1,600 sampled calls, 0 differences.

Setup on the console itself

Drop a disc image on the memory card and the game reads the CD filesystem on first launch, including raw .bin sectors, extracts its files and checks them. No PC tools are needed.

Runs from five original files

The port reads the game's own archives through the game's own code, exactly as in 1995. Nothing is repacked, converted or shipped. Every file is identified by size, and the program by SHA-1.

Agent on real hardware

Claude Code built each version, copied it to the Vita over USB, then read the logs back off the memory card after each play session. A person played; an agent diagnosed.

Behaviour read from the binary

Weapons, cameras, cockpit modes, pause and saving were all recovered from machine code and its keyboard tables, with no source code or manual to work from.

1995 video, in plain C

All 19 cutscenes use Cinepak. A decoder written for this port plays the player's original files with their sound, with no conversion step.

A GPU for a software renderer

The game only ever drew into a 320×200 frame in memory. The runtime now catches its polygons at the game's own drawing routines and sends them to the GPU, with a shader doing the work of its shade tables and palette.

Mods through the game's own door

The game turned out to have a built-in archive override, pod.ini. A converter now turns a 3D model into a working replacement, with baked textures, moving wings, walking legs, engine glow and a cheap far-away version. A title-screen button turns mods on and off.

Measured on a PS Vita 1000

From slideshow to playable

Each round was played on the device and reported from an on-screen frame counter. The first build dropped to 3–4 fps in explosions. The worst loading stall went from 30 seconds at 1 fps to a few seconds. The last round moved rendering from the CPU to the Vita's GPU.

Inside the renderer

The 16-pixel trick

In 1995, a perspective-correct divide for every pixel was too slow. Fury³'s texture mapper divides at the ends of each 16-pixel run and interpolates in between, and its speed depends on that choice. The native C rewrite keeps exactly the same behaviour. Move the slider to see what the spacing does to a receding wall.

Case files

The bugs that mattered

“Hose enemy crlf”

SymptomThe game quit while reading its enemy list, with its developers' own odd error message.
CausePart of the C library falls through into the next function. The translator wrote a return there, so a saved register came back wrong.
FixOne translator change corrected 61 sites at once.

85% of every frame

SymptomAbout 14 fps on a laptop, with no obvious heavy work.
CauseA native profiler showed debug-switch lookups through getenv sitting in the hottest paths.
FixA cached lookup. Flight fell to 1.6–3.5 ms of CPU per frame.

1 fps at the loading bar

SymptomLoading fell to 1 fps for 30 seconds on the Vita.
CauseEach memory-card call is slow, and a mission opens its archive 628 times with about 25,000 small seeks and reads.
FixA startup file index, a path cache, pooled handles and a 64 KB read window: 628 opens became 21.

“Model read hose”

SymptomRun from clean CD files, the game crashed while loading models.
CauseAn early shortcut had replaced the game's archive lookup, and unpacked files had hidden the damage ever since.
FixThe shortcut was deleted, and the game's own code now runs.

Saving never worked

SymptomNo save file ever appeared, in any build.
CauseThe game opens a Windows “Save As” dialog, and that was an empty placeholder that always cancelled.
FixOne save slot, chosen without a dialog. Square saves while paused.

The flashing title

SymptomThe title screen blinked on and off once a second.
CauseThe game redraws its title once a second. An old 500 ms fallback kept swapping in a stale buffer between redraws.
FixThe fallback now stops for good once the game has drawn its first frame.

The boss that couldn't be hurt

SymptomWith its four shields destroyed, the first boss still took no damage from any weapon.
CauseTranslated sscanf lost the comma after the first number, so every hit spot on the boss loaded with a size of zero.
Fixsscanf now shares the runtime's own reader. A log from the device pointed to it, and the boss then fell on the Vita.

Retry Mission (Y/N)

SymptomAfter losing the last life, the prompt ignored every button, then dropped to the title.
CauseIt waits for a typed character from Windows, which a handheld has no way to send.
FixCross or Start retries and Circle quits, and the prompt now says so.

Behind a distant building

SymptomOn the GPU, shooting a far-off building put the player's ship behind it.
CauseThe game's depth only sorts a model against itself and clears before each one. One shared GPU depth buffer broke that rule.
FixEach model now gets its own slice of GPU depth, while the ground stays outside it.

Workflow

How this was done with Claude Code

One person with a Vita directed the project, and Claude Code did the engineering in their terminal, with access to the code, the build tools and the memory card. The work ran as a repeating loop.

  1. Set the goal and the standard

    The opening instruction fixed the rule for everything that followed: “Keep debugging forward with real root-cause fixes (not workarounds).” It also told Claude not to stop and ask whether to continue.

  2. Read the machine code

    With no source code, Claude read the disassembly directly: jump tables, key tables and memory addresses, then traced each symptom back to a cause.

  3. Build a tool for each question

    Frame snapshots, a per-function profiler, scripted key presses, file-open logs and the byte-exact verifier were each written when a question needed them. Most bugs were found and confirmed without a person testing them.

  4. Build, deploy, measure

    Claude rebuilt for Windows, Linux or Vita, verified the result, and copied it to the memory card with a hash check. Anything that could only be judged by hand went to the person with the Vita.

  5. Play it and report back

    The person played and described what they saw. Claude paired that report with the device logs:

    “it got to terran loading screen - halfway in the loading bar - and then dropped to 1fps for several seconds”Play-test report that led to the file index and path cache

  6. Write it all down

    Every root cause went into a running handoff log, which is what let the work continue across long sessions. The process itself is now saved as a reusable skill for the next port.

Beyond this engine

What carries to the next game

The method is not tied to Fury³'s engine. It works on x86 machine code, so it applies to any 32-bit Windows game, whatever engine it uses. Most of the 7,200 or so runtime lines know nothing about Fury³, though the GPU renderer and planet select rely on its addresses, so that share has grown. A game on the same engine, such as Hellbender (1996), would reuse more, but even that needs its own addresses and testing.
